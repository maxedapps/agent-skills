Plan completion lifecycle

  1. Close implementation — finish tracked tasks, checks, and plan-backed review.
  2. Generate the report — invoke create-changes-report for repository changes.
  3. Re-enter closure if needed — disposition, fix, check, and review any material issue found while gathering report evidence.
  4. Clean up last — retire worktrees, processes, and runtime state, including report-triggered work.
  5. Hand off — make the final HTML path primary; state the fallback when the skill is unavailable.

Key code, briefly

1 · Automatic report gate ◆

This ordering keeps final cleanup after any fix cycle triggered by report evidence.

skills/implement-plan/SKILL.md 
5. When repository files changed, use `create-changes-report`
   after final checks to create the verified HTML review artifact.
   If its evidence gathering exposes a material issue, return to
   disposition, checks, and review before regenerating it.
6. Final cleanup — worktrees, branches, processes, runtime state,
   including anything created by a report-triggered fix cycle.

2 · Target-aware worktree synchronization ◆

The branch named by the task—not a hardcoded default—is always the source of synchronization.

skills/use-worktrees/SKILL.md 
- Sync direction during work is always target branch → worktree branch
  (`git merge <target-branch>` inside the worktree).
- Never rebase or rewrite shared branches.
- After every sync, run the repository's full check suite.

3 · Finding authority stays with the owning workflow

The report presents evidence; it cannot silently override review or plan closure.

skills/create-changes-report/SKILL.md 
This artifact does not replace `code-review` or an owning workflow's
finding authority. If report preparation uncovers a new material defect,
stop, return it to the owning workflow for disposition and verification,
then regenerate the report from the resolved state.
